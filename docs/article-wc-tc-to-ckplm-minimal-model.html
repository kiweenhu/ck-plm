CK-PLM 极简版本迭代模型架构设计解析

从 Windchill 和 Teamcenter 的经验出发，用极简的架构管理 Branch、Revision、Iteration、View 和 BOM 行

开源 PLM 架构设计 落地方案
做了多年 Windchill 实施，也研究过 Teamcenter 的对象模型，之后从 0 到 1 建设国产替代 PLM 时，发现一个朴素的道理：最好的架构不是面面俱到，而是极简，满足行业要求，同时保证未来的扩展。

PLM 版本管理到底在管什么

不管用 Windchill 还是 Teamcenter，PLM 的版本管理本质上要回答五个问题：

  • Revision（版本）——这是第几版？A、B、C，每次正式发布递增
  • Branch（分支）——走哪条开发线？同一版本下的并行演进路径
  • Iteration（迭代）——这版改了几次？.1、.2、.3，检出-检入循环中递增
  • View（视图）——你站在哪个角度看？设计 BOM、制造 BOM、采购 BOM
  • BOM 行——里面装了什么？子件、数量、单位、行号

这五个维度交织在一起，数据量是爆炸性的。同一个部件：3 个版本 x 2 条分支 x 每分支 5 个迭代 x 2 个视图 x 每视图 20 行 BOM = 1200 条记录。模型设计不好，查询和维护都是噩梦。

Windchill 和 Teamcenter 各自给出了答案，它们用了几十年积累出复杂的对象模型。CK-PLM 作为开源产品，需要一条不同的路。

两条老路：Windchill 和 Teamcenter 怎么做的

Windchill（对象实例分离）vs Teamcenter（BVR 容器分离）

两者的差异看似是技术细节，实则是一个根本性的设计选择：View 放在哪一层。

Windchill 的核心是两张表：WTPartMaster 管身份（number、name），WTPart 同时管版本号、迭代号和视图。同一 number 不同 View 就是不同的 WTPart 对象，各自有独立的版本链和迭代链。好处是视图级独立性强（Design 可以走 A.4 而 Mfg 停在 A.2），代价是属性冗余高、同步成本大。

Teamcenter 把 View 放在 BVR 容器上——同一 ItemRevision 下挂多个 BVR，每个 BVR 装一套 BOM 结构。好处是模型简洁、属性共享，代价是迭代隐式不可寻址，做不到视图级独立迭代，版本升级时所有视图同步推进。

第三条路：CK-PLM 的三表迭代模型

基于架构至简的道理，CK-PLM 采用对象实例分离的设计模式——Part、PartIteration、Bom_links。在此基础上，CK-PLM 还增加了 BOM 获取效率的架构设计，让大规模 BOM 的渲染和查询不再依赖应用层缓存。

核心三表 + BOM 效率扩展：快照表、解析列、Diff 表按需引入，不改动基础结构

五个维度怎么管

Revision + Branch + Iteration + View：在同一张表里管理

CK_PART_ITERATION 表同时管版本号（version 列，A/B/C）、迭代号（iteration_number 列，1/2/3）和视图（view 列，design/mfg）。每行就是一个 (view, version, iteration) 组合，如 Design A.3。这和 Windchill 的 WTPart 完全一样——WTPart 也是同时管 versionIdentifier、iterationIdentifier 和 view。

Branch（分支）在同一张表里通过 branch_id 列管理——默认值 '0' 表示主线，需要并行研发时从某个版本分叉出新分支。这是按需扩展的设计：基础三表不包含 branch_id，当业务真正需要并行分支时加一列即可，不影响已有结构。

典型场景：产品版本 A 已发布，标准产品继续迭代（主线 branch_id='0'），同时客户要求定制变型（分叉 branch_id='custom_001'）。两条线各自独立迭代，同一个 (version, iteration, view) 但 branch_id 不同，互不影响。最终可以各自发布，也可以将定制分支的修改合并回主线后递增版本到 B。

大多数 PLM 实施项目用不到分支——单线版本迭代就够用了。CK-PLM 把 Branch 设计成按需扩展：不需要时没有 branch_id 列，需要时加一列，默认值 '0' 让所有已有数据自动归入主线，零迁移成本。

做法身份层版本+迭代+视图层是否分表
WindchillWTPartMasterWTPart (version+iteration+view)身份与版本迭代分表
CK-PLMCK_PARTCK_PART_ITERATION (version+iteration+view)身份与版本迭代分表
TeamcenterItemItemRevision (仅version, 无view/显式迭代)身份与版本分表，无独立迭代

CK-PLM 认为迭代是在版本下产生的——version 是父概念，iteration 是子概念。但物理上两者合在一张表里，没有拆成独立的 version 表和 iteration 表。View 也在这张表上，不同 view 就是不同的迭代行。Windchill 也是如此。

检出 = INSERT 新迭代行

这是整个模型最精妙的部分——检出不是"锁住"已有行，而是 INSERT 一个新的迭代行作为工作副本。 原有的已发布版本数据完全不动。

以编号 100-001 的电机部件为例，当前 Design 视图版本 A 已发布到第 3 次迭代（Design A.3）。

检出

Step 1：工程师张三检出 Design A.3

INSERT 一个新的迭代行 Design A.4，从 A.3 深拷贝所有属性。原 A.3 行完全不动。

-- 检出 = INSERT 新迭代行
INSERT INTO ck_part_iteration (part_id, version, iteration_number, view,
                            is_checked_out, checkout_user,
                            checkout_at, lifecycle_state, created_by)
VALUES (
    (筛选 part number='100-001' 的 id),
    'A',                              -- 版本不变
    4,                              -- A.3 -> A.4
    'design',                       -- 视图不变
    true,                           -- 标记检出
    'zhangsan',
    CURRENT_TIMESTAMP,
    'INWORK',                  -- 强制 INWORK
    'zhangsan'
);
视图版本迭代状态检出人说明
designA.1RELEASED-历史迭代
designA.2RELEASED-历史迭代
designA.3RELEASED-原行不动
designA.4INWORKzhangsan工作副本
检入

Step 2：张三检入 Design A.4

只需两条 UPDATE——关闭检出标记 + 触发状态流转。不需要"合并工作副本"，A.4 本身就是最终数据载体。

-- 检入 = 关闭检出标记
UPDATE ck_part_iteration
SET is_checked_out = false,
    checkout_user = NULL,
    checkin_note = '增加紧固件子件，数量4个',
    lifecycle_state = 'REVIEW'
WHERE id = (Design A.4 的 id);
撤销检出

替代路径：撤销检出（DELETE）

改到一半发现问题不想检入了？DELETE 掉 A.4 这行即可。原 A.3 纹丝不动，自动恢复为最新迭代。

-- 撤销检出 = DELETE 工作副本
DELETE FROM ck_part_iteration
WHERE id = (Design A.4 的 id);
-- ck_bom_links 的 A.4 BOM 行通过 CASCADE 自动清理
三种结果的 SQL 语义：检入=UPDATE，撤销检出=DELETE。核心原因是检出时 INSERT 了独立的工作副本行——这就是 Windchill "乐观检出"模型的精髓，CK-PLM 完整继承了这一点。

View：在迭代对象上，和 Windchill 一致

同一个部件，设计工程师看 EBOM，工艺工程师看 MBOM，采购员看采购 BOM。三套 BOM 结构可以完全不同——它们属于同一个部件的不同视图迭代。

CK-PLM 把 View 放在 CK_PART_ITERATION 上——和 Windchill 的 WTPart 完全一致。同一 number 不同 View 就是不同的迭代行：Design A.3 和 Mfg A.2 是表中两条独立记录，各自有独立的版本链、迭代链和 BOM 结构。

同一部件的 Design A.4（4子件）vs Mfg A.2（5子件）——独立迭代行，各自独立BOM

查询某个视图的 BOM 时，先定位该视图的迭代，再查 BOM 行：

-- 查 EBOM（设计 BOM）
SELECT p.number, p.name, b.quantity, b.unit
FROM ck_bom_links b
JOIN ck_part p ON p.id = b.child_part_id
WHERE b.parent_iteration_id = (
    SELECT id FROM ck_part_iteration
    WHERE part_id = ? AND view = 'design'
    ORDER BY version DESC, iteration_number DESC LIMIT 1
);

-- 查 MBOM（制造 BOM）
SELECT p.number, p.name, b.quantity, b.unit
FROM ck_bom_links b
JOIN ck_part p ON p.id = b.child_part_id
WHERE b.parent_iteration_id = (
    SELECT id FROM ck_part_iteration
    WHERE part_id = ? AND view = 'mfg'
    ORDER BY version DESC, iteration_number DESC LIMIT 1
);

因为 View 在迭代对象上，不同视图天然是不同的迭代行——Design 可以走 A.4 而 Mfg 停在 A.2，两条迭代链完全独立。这和 Windchill 的行为完全一致：Per-view 独立迭代天然支持，BOM 结构天然按视图隔离。

BOM 行：挂在迭代上，支持精确引用

CK_BOM_LINKS 的 parent_iteration_id 指向某个具体迭代——这意味着 BOM 结构是和迭代绑定的，每次检出修改 BOM 都会创建新的 BOM 行集合，不会污染历史版本的 BOM。BOM 行不需要 view 列，因为迭代本身已经携带了 view 信息。

而 child_iteration_id 的可空设计，实现了精确/非精确引用能力：

引用方式child_iteration_id语义适用场景
精确引用NOT NULL锁定到子件某个迭代已发布基线、合规追溯
非精确引用NULL始终取子件最新版本设计阶段、快速迭代
-- 精确引用：锁定到子件 Design A.3
INSERT INTO ck_bom_links (parent_iteration_id, child_part_id,
                          child_iteration_id, quantity)
VALUES (
    (父件 Design A.4 的 iteration id),
    (子件 100-005 的 part id),
    (子件 100-005 的 Design A.3 iteration id),   -- 精确锁定
    2.0
);

-- 非精确引用：跟随子件最新版本
INSERT INTO ck_bom_links (parent_iteration_id, child_part_id,
                          child_iteration_id, quantity)
VALUES (
    (父件 Design A.4 的 iteration id),
    (子件 100-005 的 part id),
    NULL,                                -- 跟最新
    2.0
);
BOM 效率扩展

三表之外，按需引入效率机制

核心三表解决"对不对"的问题，BOM 渲染效率解决"快不快"的问题。CK-PLM 在不动基础三表的前提下，通过加列和加表提供三个效率扩展点：

  • CK_BOM_LINKS.resolved_iteration_id：非精确引用（child_iteration_id = NULL）的解析缓存。渲染时直接 JOIN，不再为每行跑"子件最新迭代"子查询。
  • CK_BOM_SNAPSHOT：RELEASED 迭代检入时预计算整棵 BOM 树的 JSONB 快照。已发布 BOM 的渲染 = 一行读取，零递归。
  • CK_BOM_DIFF：检入时预计算相邻迭代之间的 BOM 差异（added/removed/changed）。版本对比视图直接读，不再两次全量查树。

这三个扩展都是可选的——系统刚上线时只跑核心三表就能工作；数据量变大、BOM 渲染变慢时再加。复杂度按需生长，不会因为未来的性能需求而拖累早期的简洁性。

CK-PLM 与 Windchill 的真正差异

不是架构差异，是命名和概念表述差异。Windchill 的 WTPartMaster、WTPart、WTPartUsageLink 带着浓厚的 PTC 技术风格，对非 Windchill 用户不友好。CK-PLM 用 Part、PartIteration、Bom_links——任何有制造业背景的人一眼就能看懂。架构上完全一致，降低了理解和贡献的门槛。

复杂度按需生长

三张表是起点，不是终点。每个新需求来了，加一个列或加一张表就解决，不动已有结构。

新需求怎么加影响已有结构吗
版本分支（并行研发）ck_part_iteration 加 branch_id 列否，默认 0
视图层级关系新建 ck_view_def 表否，纯新增
替代件关系新建 ck_part_alternate 表否，纯新增
文档关联新建 ck_part_doc_link 表否，纯新增
IBA 软类型属性新建 ck_part_attr_value 表否，纯新增

这就是"复杂度按需生长"的核心理念——三张表能跑就先跑，真有需求再加。 每个需求只动一个点，不碰其他东西。已部署的系统升级时，只需要 ALTER TABLE ADD COLUMN 或 CREATE TABLE，不需要停机迁移。

总结
Part、PartIteration、Bom_links。迭代是一等公民，View 在迭代对象上，复杂度按需求生长。
  • CK_PART 管"这是哪个部件"——身份层，number 全局唯一，对应 Windchill 的 WTPartMaster
  • CK_PART_ITERATION 管"哪个视图的哪个版本的哪次迭代"——同时管理 version(A/B/C) + iteration(.1/.2/.3) + view，对应 Windchill 的 WTPart。乐观检出模型，INSERT/UPDATE/DELETE 三态切换
  • CK_BOM_LINKS 管"某次迭代的 BOM 结构"——挂在迭代级别（迭代本身已携带 view），child_iteration_id 区分精确/非精确引用

对开源 PLM 产品来说，简单本身就是竞争力。用户能看懂、能改、能贡献——这比架构完美重要得多。CK-PLM 不照搬 Windchill 或 Teamcenter 的全部概念，而是取与 Windchill 一致的架构 + 更贴切的业务命名——用极简的架构管理 Branch、Revision、Iteration、View 和 BOM 行，让真实需求驱动复杂度的生长。
