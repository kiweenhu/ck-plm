CK-PLM版本管理解析
之极简迭代模型架构

从 Windchill 和 Teamcenter 的经验出发，用极简的架构管理 Branch、Revision、Iteration、View 和 BOM 行

CK-PLM 开源PLM 数据模型 迭代管理
做了多年 Windchill 实施，也研究过 Teamcenter 的对象模型，之后从 0 到 1 建设国产替代 PLM 时，发现一个朴素的道理：最好的架构不是面面俱到，而是极简，满足行业要求，同时保证未来的扩展。

一、问题：PLM 版本管理到底在管什么

先说清楚 PLM 的版本管理要管的东西。一个部件从设计到制造到采购，需要管理五个维度的数据：

  • Revision（版本）：A、B、C……每次正式发布递增，代表一个里程碑式的版本节点
  • Branch（分支）：同一版本下的并行演进路径——需要同时走多条开发线时，从同一版本分叉
  • Iteration（迭代）：.1、.2、.3……检出-检入循环中递增，代表工作过程中的中间状态
  • View（视图）：设计视图（EBOM）、制造视图（MBOM）、采购视图……同一个部件在不同业务视角下的不同 BOM 结构
  • BOM 行：父件到子件的装配关系，携带数量、行号、单位等行级属性

这五个维度组合起来，数据量是爆炸性的——同一个部件可能有 3 个版本 × 2 条分支 × 每分支 5 个迭代 × 2 个视图 × 每视图 20 行 BOM = 1200 条数据记录。如果不做好模型设计，查询和维护都会变成噩梦。

Windchill 的做法是：WTPartMaster 管身份（number、name），WTPart 同时管版本+迭代+视图（同一 number 不同 view 是不同对象），WTPartUsageLink 管 BOM 行。功能强，但不同视图是不同对象，属性冗余高。

Teamcenter 的做法是：Item 管身份，ItemRevision 管版本（无独立迭代），BVR 容器管视图级 BOM。模型简洁，但迭代隐式不可寻址，做不到视图级独立迭代。

CK-PLM 的思路——Part、PartIteration、Bom_links。

二、三张表：CK_PART + CK_PART_ITERATION + CK_BOM_LINKS

核心模型就三张表。不多不少，刚好覆盖 Branch、Revision、Iteration、View 和 BOM 行的全部管理需求。

核心三表 + BOM 效率扩展：快照表、解析列、Diff 表按需引入，不改动基础结构

建表 DDL

CK_PART 身份层——管理"这是哪个部件"，对应 Windchill 的 WTPartMaster

-- CK_PART：身份层，一个 number 一条记录，跨版本不变
CREATE TABLE ck_part (
    id               BIGSERIAL PRIMARY KEY,
    number           VARCHAR(50)  NOT NULL,        -- 部件编号，全局唯一
    name             VARCHAR(200) NOT NULL,        -- 显示名称
    source           VARCHAR(10),                      -- MAKE / BUY
    part_type        VARCHAR(20)  DEFAULT 'SEPARABLE',   -- SEPARABLE/INSEPARABLE/PHANTOM
    default_unit     VARCHAR(20)  DEFAULT 'ea',
    created_by       VARCHAR(50),
    created_at       TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    UNIQUE(number)                               -- 编号全局唯一
);

CK_PART_ITERATION 版本+迭代层——同时管理 Version(A/B/C)、Iteration(.1/.2/.3) 和 View，对应 Windchill 的 WTPart

-- CK_PART_ITERATION：版本+迭代+视图层，检出时 INSERT 新行
CREATE TABLE ck_part_iteration (
    id                BIGSERIAL PRIMARY KEY,
    part_id           BIGINT NOT NULL REFERENCES ck_part(id) ON DELETE CASCADE,
    version           VARCHAR(10) NOT NULL DEFAULT 'A',    -- A/B/C，发布时递增
    iteration_number  INTEGER NOT NULL DEFAULT 1,          -- 1, 2, 3...（显示为 .1 .2 .3）
    view              VARCHAR(30),                        -- 视图：design/mfg/null（与WTPart一致）
    is_checked_out    BOOLEAN NOT NULL DEFAULT false,
    checkout_user     VARCHAR(50),                      -- 检出人
    checkout_at       TIMESTAMP,                        -- 检出时间
    checkin_note      TEXT,                             -- 检入备注
    lifecycle_state   VARCHAR(30) DEFAULT 'INWORK',    -- 迭代级状态
    created_by        VARCHAR(50),
    created_at        TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    UNIQUE(part_id, view, version, iteration_number)
);

CK_BOM_LINKS BOM 行——管理"某次迭代的 BOM 结构"

-- CK_BOM_LINKS：BOM 行，挂在迭代级别上（迭代本身已携带view）
CREATE TABLE ck_bom_links (
    id                    BIGSERIAL PRIMARY KEY,
    parent_iteration_id   BIGINT NOT NULL REFERENCES ck_part_iteration(id),
    child_part_id         BIGINT NOT NULL REFERENCES ck_part(id),  -- 子件：身份级
    child_iteration_id    BIGINT REFERENCES ck_part_iteration(id),  -- 精确引用：null=跟最新
    resolved_iteration_id BIGINT REFERENCES ck_part_iteration(id),  -- 非精确引用解析缓存
    quantity              NUMERIC(18,6) NOT NULL DEFAULT 1,
    unit                  VARCHAR(20),                          -- 用量单位
    line_number           INTEGER                               -- 行号
);

CK_BOM_SNAPSHOT Released BOM 快照——已发布 BOM 的整树物化

-- CK_BOM_SNAPSHOT：RELEASED 迭代检入时预计算，O(1) 读取整棵 BOM 树
CREATE TABLE ck_bom_snapshot (
    iteration_id   BIGINT PRIMARY KEY REFERENCES ck_part_iteration(id),
    snapshot_json  JSONB NOT NULL,           -- 完整 BOM 树（含所有层级）
    node_count     INTEGER NOT NULL,         -- 节点总数
    max_depth      INTEGER NOT NULL,         -- 最大层级
    computed_at    TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CK_BOM_DIFF BOM Diff 预计算——检入时算好，对比时直接读

-- CK_BOM_DIFF：任意两个迭代之间的新增/删除/变更行，检入时预计算
CREATE TABLE ck_bom_diff (
    from_iteration_id  BIGINT REFERENCES ck_part_iteration(id),
    to_iteration_id    BIGINT REFERENCES ck_part_iteration(id),
    diff_json          JSONB NOT NULL,       -- {added:[], removed:[], changed:[]}
    PRIMARY KEY (from_iteration_id, to_iteration_id)
);
BOM 效率扩展：按需引入，不改动基础结构

核心三表解决的是"对不对"的问题，BOM 效率扩展解决的是"快不快"的问题。resolved_iteration_id 消灭非精确引用的子查询；CK_BOM_SNAPSHOT 让已发布 BOM 零递归读取；CK_BOM_DIFF 让版本对比不再两次全量查树。三者都是加列或加表实现，不破坏原有 CK_PART / CK_PART_ITERATION / CK_BOM_LINKS 结构，符合"复杂度按需生长"的原则。

场景实战

三、场景一：检出 → 修改 → 检入

这是 PLM 最核心的操作。以一个编号为 100-001 的电机部件为例，当前 Design 视图版本 A 已发布到第 3 次迭代（Design A.3）。

检出

Step 1：工程师张三检出 Design A.3

检出不是"锁住"已有行，而是 INSERT 一个新的迭代行 Design A.4，从 A.3 深拷贝所有属性。原 A.3 行完全不动。

-- 检出 = INSERT 新迭代行，拷贝 A.3 的属性
INSERT INTO ck_part_iteration (part_id, version, iteration_number, view,
                            is_checked_out, checkout_user, checkout_at,
                            lifecycle_state, created_by)
VALUES (
    (筛选 part number='100-001' 的 id),
    'A',                                  -- 版本号不变，仍在 A 版本下
    4,                                    -- A.3 的 iteration_number=3，新迭代=4
    'design',                              -- 视图不变
    true,                                 -- 标记为检出状态
    'zhangsan',
    CURRENT_TIMESTAMP,
    'INWORK',                            -- 强制重置为 INWORK
    'zhangsan'
);

此时数据库中的迭代链：

视图版本迭代状态检出人说明
designA.1RELEASED—历史迭代
designA.2RELEASED—历史迭代
designA.3RELEASED—上一个发布版本（原行不动）
designA.4INWORKzhangsan工作副本（检出中）

版本升级（A→B）发生在正式发布时：当 A.4 通过审批后，可以发布为 A.4（RELEASED），或者升版本为 B.1。版本号在 CK_PART_ITERATION 表的 version 列上管理，不是独立的一张表。

修改

Step 2：张三在 A.4 上修改 BOM

张三在 A.4 的迭代上直接修改 BOM 行——新增子件、修改数量、删除行。所有操作直接写入 A.4 关联的 ck_bom_links 行，不需要任何中间表。

-- 张三在 Design A.4 上新增一个子件
INSERT INTO ck_bom_links (parent_iteration_id, child_part_id, quantity, unit)
VALUES (
    (筛选 Design A.4 的 iteration id),
    (筛选子件 number='200-003' 的 part id),
    4.0,
    'ea'
);

-- 修改某个子件的数量
UPDATE ck_bom_links SET quantity = 6.0
WHERE parent_iteration_id = (Design A.4 id) AND child_part_id = (某子件 id);
检入

Step 3：张三检入 Design A.4

检入只需 两条 UPDATE 语句——关闭检出标记 + 触发状态流转。不需要"合并工作副本"——A.4 本身就是最终数据载体。

-- 检入 = 关闭检出标记 + 记录检入备注
UPDATE ck_part_iteration
SET is_checked_out = false,
    checkout_user = NULL,
    checkin_note = '增加紧固件子件 200-003，数量4个',
    lifecycle_state = 'REVIEW'            -- 进入评审状态
WHERE id = (Design A.4 的 iteration id);
撤销检出

替代路径：撤销检出（DELETE）

如果张三改到一半发现问题不想检入了，撤销检出就是 DELETE 掉 A.4 这行。原 A.3 纹丝不动，自动恢复为最新迭代。

-- 撤销检出 = DELETE 工作副本
DELETE FROM ck_part_iteration
WHERE id = (Design A.4 的 iteration id);
-- ck_bom_links 中的 A.4 BOM 行通过 ON DELETE CASCADE 自动清理
三种结果路径的 SQL 语义：检入=UPDATE，撤销检出=DELETE，取消检出=DELETE。核心原因是检出时 INSERT 了独立的工作副本行——这是"乐观检出"模型的精髓。

四、场景二：EBOM 与 MBOM 的多视图管理

同一个部件，设计工程师看到的是设计 BOM（EBOM），工艺工程师看到的是制造 BOM（MBOM），采购员看到的是采购 BOM。这三套 BOM 结构可以完全不同——它们属于同一个部件的不同视图迭代。

CK-PLM 的做法和 Windchill 完全一致：View 放在 CK_PART_ITERATION 上。同一 number 不同 View 就是不同的迭代行——Design A.3 和 Mfg A.2 是 ck_part_iteration 表中的两条独立记录，各自有独立的版本链和 BOM 结构。

同一个部件的 Design A.4（4子件）vs Mfg A.2（5子件，多了紧固件）——独立的迭代行

查询某个视图的 BOM 时，先找到该视图的最新迭代，再查 BOM 行：

-- 查 EBOM（设计 BOM）：先找 Design 视图的最新迭代
SELECT p.number, p.name, b.quantity, b.unit
FROM ck_bom_links b
JOIN ck_part p ON p.id = b.child_part_id
WHERE b.parent_iteration_id = (
    SELECT id FROM ck_part_iteration
    WHERE part_id = (100-001 的 part id)
      AND view = 'design'
    ORDER BY version DESC, iteration_number DESC
    LIMIT 1
);

-- 查 MBOM（制造 BOM）：找 Mfg 视图的最新迭代
SELECT p.number, p.name, b.quantity, b.unit
FROM ck_bom_links b
JOIN ck_part p ON p.id = b.child_part_id
WHERE b.parent_iteration_id = (
    SELECT id FROM ck_part_iteration
    WHERE part_id = (100-001 的 part id)
      AND view = 'mfg'
    ORDER BY version DESC, iteration_number DESC
    LIMIT 1
);

因为 View 在迭代对象上，不同视图天然是不同的迭代行——Design 可以走 A.4 而 Mfg 停在 A.2，两条迭代链完全独立。这和 Windchill 的行为完全一致，BOM 结构天然按视图隔离，无需额外过滤。

五、场景三：BOM 精确引用与版本追溯

这是迭代作为"一等公民"的核心价值——每个迭代都有独立 ID，可以被 BOM 行精确引用。

想象一个场景：产品 A 的 BOM 引用了部件 100-005（轴承）。有两种引用方式：

精确引用（Exact Reference）

child_iteration_id 不为空，指向 100-005 的某个具体迭代（如 Design A.3）。意味着"我就用 A.3 这个版本，即使后面 100-005 升到了 A.4、A.5，我的 BOM 不变"。

-- 精确引用：BOM 行锁定到子件的 Design A.3 迭代
INSERT INTO ck_bom_links (parent_iteration_id, child_part_id, child_iteration_id,
                          quantity, unit)
VALUES (
    (父件 Design A.4 的 iteration id),
    (子件 100-005 的 part id),
    (子件 100-005 的 Design A.3 iteration id),   -- 精确锁定
    2.0, 'ea'
);

非精确引用（Non-Exact Reference）

child_iteration_id 为空，只指向 child_part_id（身份级）。意味着"始终用 100-005 的最新版本"。子件升级到 A.4 后，BOM 自动跟随。

-- 非精确引用：BOM 行跟随子件最新版本
INSERT INTO ck_bom_links (parent_iteration_id, child_part_id, child_iteration_id,
                          quantity, unit)
VALUES (
    (父件 Design A.4 的 iteration id),
    (子件 100-005 的 part id),
    NULL,                                -- 非精确：跟最新
    2.0, 'ea'
);
引用方式child_iteration_id语义适用场景
精确引用NOT NULL锁定到子件某个迭代版本已发布基线 BOM、合规追溯
非精确引用NULL始终取子件最新版本设计阶段 BOM、快速迭代

查询 BOM 时自动展开：

-- 展开 BOM，自动解析精确/非精确引用
SELECT
    child_p.number,
    child_i.version,
    CASE
        WHEN b.child_iteration_id IS NOT NULL THEN
            child_i.iteration_number                  -- 精确引用：取锁定的迭代号
        ELSE
            latest_i.iteration_number                  -- 非精确引用：取最新迭代号
    END AS iteration,
    b.quantity,
    b.unit
FROM ck_bom_links b
JOIN ck_part child_p ON child_p.id = b.child_part_id
LEFT JOIN ck_part_iteration child_i
    ON child_i.id = b.child_iteration_id                    -- 精确引用的 JOIN
LEFT JOIN ck_part_iteration latest_i
    ON latest_i.part_id = child_p.id                       -- 非精确引用：取该 part 的最新迭代
    AND latest_i.id = (
        SELECT id FROM ck_part_iteration
        WHERE part_id = child_p.id
        ORDER BY version DESC, iteration_number DESC LIMIT 1
    )
WHERE b.parent_iteration_id = ?;

六、场景四：并行设计与版本回退

并行设计（含跨视图并行）

因为 View 在迭代对象上，不同视图的迭代天然隔离。张三可以检出 Design A.4 改设计 BOM，同时李四检出 Mfg A.3 改制造 BOM——两人操作不同的迭代行，互不影响：

工程师操作数据库变化
张三检出 100-001 的 Design A.3INSERT 100-001 的 Design A.4 迭代行
李四检出 100-001 的 Mfg A.2INSERT 100-001 的 Mfg A.3 迭代行
张三修改 Design A.4 的 BOMINSERT/UPDATE ck_bom_links (parent=Design A.4)
李四修改 Mfg A.3 的 BOMINSERT/UPDATE ck_bom_links (parent=Mfg A.3)
张三检入 Design A.4UPDATE Design A.4 关闭检出标记
李四撤销检出 Mfg A.3DELETE Mfg A.3 迭代行（含级联 BOM）

同一部件不同视图的并行操作完全隔离——不同的 iteration_id，不会有任何锁竞争。这是 View 放在迭代对象上的天然优势：跨视图并行和同视图串行一样简单。

版本回退与对比

因为每个迭代都有独立 ID 和记录，可以轻松对比任意两个迭代的 BOM 差异，也可以"回退"到某个历史迭代的 BOM 结构：

-- 对比 Design A.3 和 Design A.4 的 BOM 差异
SELECT
    CASE
        WHEN old.child_part_id IS NULL THEN '新增'
        WHEN new.child_part_id IS NULL THEN '删除'
        WHEN old.quantity != new.quantity THEN '数量变更'
        ELSE '未变'
    END AS action,
    COALESCE(new_p.number, old_p.number) AS part_number,
    old.quantity AS old_qty,
    new.quantity AS new_qty
FROM ck_bom_links old
FULL OUTER JOIN ck_bom_links new
    ON old.child_part_id = new.child_part_id
LEFT JOIN ck_part old_p ON old_p.id = old.child_part_id
LEFT JOIN ck_part new_p ON new_p.id = new.child_part_id
WHERE old.parent_iteration_id = (Design A.3 id)
  AND new.parent_iteration_id = (Design A.4 id);
-- 回退：把 Design A.4 的 BOM 恢复成 A.3 的结构
DELETE FROM ck_bom_links WHERE parent_iteration_id = (Design A.4 id);
INSERT INTO ck_bom_links (parent_iteration_id, child_part_id, child_iteration_id, quantity, unit, line_number)
SELECT (Design A.4 id), child_part_id, child_iteration_id, quantity, unit, line_number
FROM ck_bom_links WHERE parent_iteration_id = (Design A.3 id);

七、场景五：并行分支与客户定制

当产品版本 A 已经发布，但需要同时走多条开发线时——比如标准产品继续迭代，同时为客户做一个定制变型——就需要 Branch（分支）。

Branch 是按需扩展的维度，基础三表不含 branch_id 列。当业务真正需要并行分支时，加一列即可：

-- 按需扩展：加 branch_id 列，默认 0 表示主线
ALTER TABLE ck_part_iteration ADD COLUMN branch_id VARCHAR(64) DEFAULT '0';

典型场景：标准产品 + 客户定制并行

100-001 电机的 Design A.3 已发布。客户要求定制版本：更换轴承型号，但标准产品的 A.4 迭代也在同步进行。

工程师操作数据库变化
张三主线检出 Design A.3INSERT Design A.4，branch_id = '0'（主线）
李四定制分支检出INSERT Design A.4，branch_id = 'custom_001'（定制分支）
张三修改主线 BOMINSERT/UPDATE ck_bom_links (parent=主线 A.4)
李四替换定制分支的轴承INSERT/UPDATE ck_bom_links (parent=定制 A.4)
张三检入主线 A.4UPDATE 关闭检出标记
李四检入定制 A.4UPDATE 关闭检出标记

同一个 version（A）、同一个 iteration（4）、同一个 view（Design），但 branch_id 不同——两条线完全独立，互不影响。最终可以各自发布，也可以将定制分支的修改合并回主线后递增版本到 B。

-- 查询某部件所有分支的最新迭代
SELECT DISTINCT ON (branch_id, view, version)
    branch_id, version, iteration_number, view, lifecycle_state
FROM ck_part_iteration
WHERE part_id = (100-001 id)
ORDER BY branch_id, view, version DESC, iteration_number DESC;
-- 分支合并：把定制分支的 BOM 差异同步到主线新版本 B.1
INSERT INTO ck_bom_links (parent_iteration_id, child_part_id, child_iteration_id, quantity, unit, line_number)
SELECT (主线 B.1 id), child_part_id, child_iteration_id, quantity, unit, line_number
FROM ck_bom_links
WHERE parent_iteration_id = (定制分支 A.4 id);
Branch 的按需哲学

大多数 PLM 实施项目用不到分支——单线版本迭代就够用了。Windchill 虽然支持 branchId，但实际项目中极少启用。CK-PLM 把 Branch 设计成按需扩展：不需要时没有 branch_id 列，需要时加一列，不影响任何已有数据和查询逻辑。默认值 '0' 让所有已有数据自动归入主线，零迁移成本。

关键认知：CK-PLM 和 Windchill 的架构基本一致——都是"身份层 + 版本迭代合并层 + BOM行层"三张表，View 都放在迭代对象上。差异仅在命名和概念表述：

身份层WTPartMaster（number, name）CK_PART（number, name）
版本+迭代+视图层WTPart（version + iteration + view 合并）CK_PART_ITERATION（version + iteration + view 合并）

View 放在哪WTPart 对象上（不同视图=不同对象）CK_PART_ITERATION 上（不同视图=不同迭代行）
核心差异命名偏技术（Master/WTPart/UsageLink）命名贴业务（Part/Iteration/Bom_links）

CK-PLM 的取舍逻辑：

能力来源CK-PLM 如何实现

CK-PLM 与 Windchill 的真正差异

不是架构差异，是命名和概念表述差异。Windchill 的 WTPartMaster、WTPart、WTPartUsageLink 带着浓厚的 PTC 技术风格，对非 Windchill 用户不友好。CK-PLM 用 Part、PartIteration、Bom_links——任何有制造业背景的人一眼就能看懂。架构上完全一致，降低了理解和贡献的门槛。

九、复杂度按需生长

三张表是起点，不是终点。每个新需求来了，加一个列或加一张表就解决，不动已有结构。

新需求怎么加影响已有结构吗
版本分支（并行研发）ck_part_iteration 加 branch_id 列否，默认 0
视图层级关系新建 ck_view_def 表（含 parent_view_id）否，纯新增
替代件关系新建 ck_part_alternate 表否，纯新增
文档关联新建 ck_part_doc_link 表否，纯新增
IBA 软类型属性新建 ck_part_attr_value 表（EAV 模式）否，纯新增

这就是"复杂度按需生长"的核心理念——三张表能跑就先跑，真有需求再加。每个需求只动一个点，不碰其他东西。已部署的系统升级时，只需要 ALTER TABLE ADD COLUMN 或 CREATE TABLE，不需要停机迁移。

十、总结

CK-PLM 的三表迭代模型，核心理念就一句话：Part、PartIteration、Bom_links。迭代是一等公民，View 在迭代对象上，复杂度按需求生长。
  • CK_PART 管"这是哪个部件"——身份层，number 全局唯一，对应 Windchill 的 WTPartMaster
  • CK_PART_ITERATION 管"这个部件的哪个视图的哪个版本的哪次迭代"——同时管理 version(A/B/C) + iteration(.1/.2/.3) + view，对应 Windchill 的 WTPart。乐观检出模型，INSERT/UPDATE/DELETE 三态切换
  • CK_BOM_LINKS 管"某次迭代的 BOM 结构"——挂在迭代级别（迭代本身已携带 view），child_iteration_id 区分精确/非精确引用

对开源 PLM 产品来说，简单本身就是竞争力。用户能看懂、能改、能贡献——这比架构完美重要得多。Windchill 和 Teamcenter 用了二十年积累出复杂的对象模型，CK-PLM 不需要从头复制它们。三张表起步，与 Windchill 一致的架构 + 更贴切的业务命名，让真实需求驱动复杂度的生长，才是开源产品的正确姿势。
